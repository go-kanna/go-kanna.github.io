// 魔法ではない、
// 生成された Go。

バリデーション、値オブジェクト、データベース、マッピング、メッセージ、依存関係の組み立て、テストデータ。Go のサービスならどこでも繰り返すものを引き受ける、7 つのコードジェネレータです。構造体タグからスキーマまで、すでに書いたものを読み取り、本来手で書くはずの素の Go を生成します。

kanna-validate構造体タグからバリデーション kanna-valueルールを守る値オブジェクト kanna-orm素の SQL のリポジトリ kanna-mapperドメインからワイヤへ、フィールド単位で kanna-i18n型付き関数になるメッセージ kanna-di登録なしで依存関係を組み立て kanna-fixture全フィールドが埋まったテストデータ

それぞれが独立したモジュールです。1 つだけでも、showcase のように 7 つ全部でも使えます。全部使うときは kanna gen が順に実行します。

kanna-validateREADME を読む

kanna-validate は、構造体の validate タグから Validate メソッドを生成し、違反を Rails のエラーコードで、フィールドの JSON 名をキーにして報告します。

タグの書き方は go-playground/validator と同じです。ただし呼び出しのたびにリフレクションで読むのではなく、go generate のときに 1 度だけ読みます。

README を読む GitHub v0.0.7Go 1.27

go get -tool github.com/go-kanna/validate/cmd/kanna-validate
kanna-valueREADME を読む

kanna-value は、値を 1 つ保持する構造体と validate メソッドから値オブジェクトを生成します。コンストラクタ、アクセサ、JSON と SQL のメソッドがそろい、値がどこから来てもルールを守らせます。定数を持つ string 型に //kanna:enum を付ければ、定数の値だけを読み込む enum になります。

値オブジェクトごとに書くはずのコンストラクタと 4 つのマーシャリングメソッドを、ルールを 1 箇所にまとめて生成します。各レイヤで繰り返すはずの enum の定数チェックも不要になります。

README を読む GitHub v0.0.4Go 1.26

go get -tool github.com/go-kanna/value/cmd/kanna-value
kanna-ormREADME を読む

kanna-orm は、リポジトリのインターフェースの実装を、SQL をリテラルのまま含めて生成します。テーブルごとのスコープ型も生成し、そのメソッドで絞り込み、並べ替え、ページング、リレーションの読み込みができます。

スコープは gorm のようにつなげられ、クエリは sqlc のようにスキーマと照合され、生成コードにリフレクションはありません。PostgreSQL（pgx または database/sql 経由）と MySQL 8.4 以降に対応します。

README を読む GitHub v0.0.3Go 1.26

go get -tool github.com/go-kanna/orm/cmd/kanna-orm
kanna-mapperREADME を読む

kanna-mapper は、ドメイン型と、自分では管理しないワイヤ型（protobuf などの通信用の型）の間の関数を生成します。シグネチャを宣言すれば、本体をフィールドごとに生成し、protobuf の oneof、enum、直和型も扱います。

宣言のしかたは goverter に近いものです。Go が自力で変換できないものは、変換する関数を uuid.Parse や timestamppb.New のまま並べます。

README を読む GitHub v0.0.7Go 1.26

go get -tool github.com/go-kanna/mapper/cmd/kanna-mapper
kanna-i18nREADME を読む

kanna-i18n は、ロケールファイルのディレクトリをコンパイルし、メッセージごとに型付きのコンストラクタを生成します。翻訳もコードに組み込まれます。CLDR の複数形、ロケールに合わせた数値の書式、Accept-Language の値を受け取る Localizer を備えています。

ロケールファイルは go-i18n と同様ですが、メッセージは実行時に ID で引くものではなく、コンパイラがチェックする関数です。

README を読む GitHub v0.0.7Go 1.26

go get -tool github.com/go-kanna/i18n/cmd/kanna-i18n
kanna-diREADME を読む

kanna-di は、型の隣にある関数から、依存する順に呼び出すコンテナ構造体のコンストラクタを生成します。プロバイダが開いたものは、コンストラクタが返す 1 つのクリーンアップで閉じます。

Wire と同じくコンパイル前に生成しますが、管理するプロバイダセットはありません。依存は型の隣にある関数から得られ、インターフェースはタグ 1 つでバインドします。

README を読む GitHub v0.0.5Go 1.26

go get -tool github.com/go-kanna/di/cmd/kanna-di
kanna-fixtureREADME を読む

kanna-fixture は、パッケージのすべての構造体について、全フィールドが埋まったコンストラクタを生成します。値は衝突しないよう連番にし、validate タグのルールの範囲で埋め、指定すれば gofakeit のテンプレートから作ります。

どのテストパッケージでも増えていく newTestUser ヘルパーを、すべての構造体について生成し、構造体の変更にも追従します。フィクスチャは作った時点で有効なので、1 つのルールのテストでは 1 つのフィールドを変えるだけです。

README を読む GitHub v0.0.7Go 1.26

go get -tool github.com/go-kanna/fixture/cmd/kanna-fixture

1 つ覚えれば、7 つとも使える

どのツールも、インストール、実行、CI でのチェックの手順は同じです。設定するのは、実行する 1 行だけです。

  1. モジュールにインストールする

    go get -tool github.com/go-kanna/validate/cmd/kanna-validate

    バージョンは go.mod に記録されるので、プロジェクトの全員が同じものを実行します。

  2. 読み取る対象に印を付ける

    //go:generate go tool kanna-validate

//kanna:validate
type CreateUserRequest struct {

    対象の構造体、インターフェース、ディレクトリの隣にコメントを書きます。kanna がなくても、コードの読み方は変わりません。

  3. 生成する

    go generate ./...

    各ツールは _gen.go ファイルを書き出し、成功したら何も出力しません。間違いがあれば止まり、ファイルと行、おそらく意図した内容を示します。

  4. CI でチェックする

    KANNA_CHECK=1 go generate ./...

    コミットされたファイルが、ジェネレータが今書き出す内容と違えば失敗します。このとき何も書き出しません。

7 つとも、必要な順に

ツールは他のツールが書いたものを読むので、2 つ以上使うと実行の順序が問題になります。kanna gen は、各ツールが読むものと書くものから順序を求め、//go:generate go tool kanna-* の行を 1 回ずつ実行します。設定は不要で、パッケージの一覧を管理する必要もありません。

  • 理由を見る

    go tool kanna gen --plan

    実行するものと、その位置にある理由を表示します。たとえば code in usecase calls what kanna-validate generates のように示し、何も実行しません。

  • CI でチェックする

    go tool kanna gen --check

    コミットされたファイルが、生成される内容と違えば失敗します。このとき何も書き出しません。

  • インストールする

    go get -tool github.com/go-kanna/kanna

    実行するのはコードにすでにある行なので、これがなくても各ツールは go generate で今までどおり動きます。README を読む

すべてのジェネレータが守る、Go の 3 つのことわざ

ツールの仕事はそれぞれ違っても、守るルールは同じ 3 つです。

  • Clear is better than clever.

    ジェネレータが書くのは、自分で書くはずのコードです。if 文、関数呼び出し、文字列リテラルの SQL です。デバッガでステップ実行でき、ルールの変更はすべて diff に現れます。

  • Reflection is never clear.

    構造体タグ、ディレクティブ、ロケールファイルは、呼び出しのたびにリフレクションで読むのではなく、go generate のときに 1 度だけ読みます。実行されるのは、生成ファイルに書かれているコードそのものです。

  • A little copying is better than a little dependency.

    生成コードは自分のモジュールの中にある、自分のコードです。kanna-di と kanna-mapper は実行時に何もインポートしません。ランタイムが必要なジェネレータは小さなものを同じモジュールで提供するので、両者がずれることはありません。

Rob Pike の Go Proverbs より。

7 つのツール、1 つのサービス

go-kanna/showcase は、PostgreSQL を使う gRPC の ToDo サービスで、すべてのツールがそれぞれの持ち場で働いています。ジェネレータが生成したものはコミットされているので、各ファイルを生成元と並べて読めます。ここでは木の色で示しています。

  • kanna-validateユースケースへの入力と、環境変数から読んだ設定をチェックします
  • kanna-valueToDo の完了日時をどこでも 2000 年から 2100 年の間に保ち、優先度を宣言した 3 つのいずれかに保ちます

  • kanna genmake gen の裏で全部を実行し、コミットされた内容を CI でチェックします

    GitHub pkg.go.dev

なぜ鉋なのか

鉋（kanna）は、板の上を手前に引いて削る日本の道具です。良い鉋は向こうが透けるほど薄い削り屑を出し、それ以上手を加える必要のない面を残します。

ジェネレータに求める仕事も同じです。自分で書くはずのコードだけを、読めるほど薄く削り出し、プログラムの他の部分には手を付けません。削り屑はこのロゴになり、その木の色は、このサイトでジェネレータが書いたものすべての色になっています。
